Security

We welcome responsible reports that help protect Notin users.

Report privately

Email security@notin.app with the affected URL, reproducible steps, impact and any supporting material. Do not include another person’s note content, credentials or tokens unless strictly necessary.

Safe-harbor expectations

Use test accounts and the minimum data required. Do not use denial of service, social engineering, persistence, destructive actions, automated mass scanning or access to data beyond what proves the issue. Allow reasonable time for investigation before disclosure.

Current security model

  • HTTPS is required in production.
  • Access tokens are short lived (15m, memory-only) with token-version invalidation on password reset; refresh sessions rotate with family-based replay detection (10s grace for benign race, full family nuke on replay).
  • Signed double-submit CSRF (notin_csrf) + trusted-origin guard on refresh/logout; all other routes use Bearer auth.
  • Password policy: 8–72 bytes, 3-of-4 categories (lower/upper/number/symbol), common blocklist, no sequential/repeating, no email/username containment; strength evaluated via /api/auth/password-strength.
  • Device inventory: active sessions capture user-agent and IP, listable via /api/auth/sessions, revocable per device or revoke-others.
  • Notes are account-scoped, optimistic concurrency via expectedUpdatedAt → 409 on conflict, quotas (5000 notes, 250MB storage, 10 images/note).
  • Attachments: PNG/JPEG/WebP/GIF ≤5MB, magic-byte check, random filenames, storage abstraction local (default) + S3/R2 provider, owner-only serving.
  • Public shares use 32-byte random secrets, SHA-256 at rest, revocable/rotatable, 30-day TTL, scoped file access, trashed→404.
  • Notin is not end-to-end encrypted; authorized infra can process note content.
  • Production AI features may send bounded note content to the configured provider when invoked; per-user rate limits prevent NAT starvation.
  • Expired OTP/reset/revoked tokens cleaned hourly via cleanup job (POST /api/auth/cleanup) and on startup.

Response targets

The operator should acknowledge valid reports within three business days and provide status updates for high-severity issues. These targets must be staffed before public launch.
